## MATRIZ RIESGO WIREGUARD (auditoria 2026-08-03)

- Tunel wg0 es del KERNEL (wireguard), independiente de zpot.
  Reiniciar zpot NO afecta el tunel.
- Rutas Alpine: `10.7.0.0/24 dev wg0` + default via 192.168.2.1 (eth0).
- ip rules MWAN: fwmark 0x1->wan1, 0x2->wan2. No tocan 10.7.0.0/24.
- nft PROTEGE el WG (NO BORRAR):
  - `iif "wg0" ip daddr 10.7.0.0/24 accept`
  - `iif "eth3" ip daddr {10.7.0.0/24, 192.168.20.0/24} drop`
  - `iifname "ppp*" ip daddr {10.7.0.0/24, 192.168.10.0/24} drop`
- RIESGO REAL: host saturado (load 7-8, softirq) -> timeouts SSH
  transitorios (el tunel sigue OK: ping 160ms, handshake 2s).
- Mitigacion deploy: el binario nuevo NO cambia logica de red en
  arranque (fix = spawn_blocking, mismo comportamiento).
- Recovery si se pierde SSH: tunel lo mantiene Alpine (endpoint VPS);
  zpot no toca ruta al endpoint. No hay out-of-band -> deploy por
  fases con verificacion en cada paso.

  reconexion): la sesion vieja quedaba y shared_users bloqueaba al cliente

- H4 (BUG-E/20): el set nft hotspot_auth (timeout 1d) NO se renovaba ->

  sobre elemento existente NO renueva el timeout (no-op). Fix: delete+add
  SOLO cuando el elemento esta por expirar (>22h desde ultimo add, campo
  nft_expire en la sesion) — 1 renovacion por sesion cada 22-24h, ventana
  de redirect ~10ms imperceptible. VERIFICADO: delete+add renueva
  (23h55m -> 23h59m59s).
- H5 (BUG-F): send_accounting panica (index out of bounds) si gw no tiene

- H6 (2026-08-04, commit c018072): shared_users — el login nuevo GANA.
  Antes con limite=1 el segundo dispositivo era RECHAZADO ("Session limit

  antigua(s) del mismo usuario (accounting stop + limpieza) hasta dejar
